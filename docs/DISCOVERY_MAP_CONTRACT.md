## Data, privacy, and lifetime invariants

- `DiscoveryMapPoint.id` is the composite subject/point identity. The UI supplies region-classified points; the adapter filters again by the selected provider. Unknown regions never enter an SDK.
- `dataVersion` identifies the coordinate/member set, including any caller-side filtering. Detail-only title/image changes do not reconstruct the spatial index. `FitAll.pointIds` frames a subset of the full data set without clipping outliers.
- Canonical points and user selections remain WGS84. Google receives those doubles directly. AMap conversion happens only after the existing privacy gate is ready; the cached display result is never persisted as a point or returned as a route target. Existing already-GCJ-02 route geometry helpers are untouched.
- `DiscoveryCameraPosition` is explicitly a provider-tagged view-only position. Restoring an AMap camera does not treat its display centre as a WGS84 pilgrimage point. Commands to locate the user accept WGS84 and convert through the same provider adapter.
- The existing `SingleLiveMapCoordinator` retires the old map before acquiring the next provider. Neither adapter instantiates a second map. Disposal detaches listeners and removes only its own markers.
- No automatic reframing occurs on metadata, theme, selection, or panel updates. A first Google map with no camera command uses an authored country overview. Explicit restore/location commands take precedence. Navigation follow remains owned by the navigation session.

## Computation and rendering invariants

- The latitude-band index uses sorted longitude ranges, splitting date-line intervals into two disjoint queries. Duplicate composite identities are rejected; separate subjects with the same bare point ID remain distinct.
- Camera idle is debounced for 300 ms. A generation token includes data version, provider, and monotonically increasing request number. Movement immediately invalidates it; cancellation and token checks precede publication. Index construction/query and clustering check cancellation on workers.
- SDK coordinate conversion, projection, and marker updates remain on Main. Long loops yield after approximately 4 ms of work and retain every element. This is a scheduling budget, not a claim that an individual native call or a device frame always completes in 4 ms.
- Every visible member occurs in exactly one count cluster. Cluster anchors use a real member's geographic coordinate, not an arithmetic longitude average. No point limits, distance clipping, or priority pruning are used.
- Images and labels are optional collision-tested decoration. Turning images off, missing images, and load failure leave the original marker/count intact. The image workload has three concurrent requests, an 8 MiB local decoded-image cache, HTTPS host validation, and a bounded failure cache. Images are requested only for currently visible decorated markers. No main-site data fetch is caused by panning.
- Stable IDs drive add/update/remove differences; a visual selection or successful image load updates an existing marker. At maximum SDK zoom a cluster tap returns every member to the shared panel.

## Verification and honest boundaries

`DiscoveryMapEngineTest` covers date-line and brute-force range equivalence, composite identity, stale generations, member conservation with images off/unavailable, decoration avoidance, exact overlap, selection and stable deltas, and measured camera pan. Its synthetic scale test runs 1,000, 10,000, and 100,000 points and emits aggregate index/query/cluster/delta durations and marker counts. It does not emit real coordinates or titles.

Execution results are recorded in the frontend acceptance report after the coordinated build. Pure JVM timing is not SDK rendering, frame-time, accessibility, screenshot, or device evidence. API 26/37 native projection/anchor, dense-map memory and frame timing, rotation, font scale and TalkBack require the dedicated emulator checks; none are represented as completed by this document.

## Diagnosis notes

- Official Google Navigation SDK `Marker`, `GoogleMap`, `Projection`, `MarkerOptions` and map-loaded callback documentation was rechecked on 2026-09-20 before the native-test and callback refinements: SDK operations remain on Main, projection is relative to the map view, anchors are normalized against bitmap dimensions, and a one-shot map-loaded callback cannot be treated as an offline marker-update completion signal. Android `UiAutomation` documentation confirms the default suppresses other accessibility services; the TalkBack test uses `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES` and explicitly verifies the service remains active.
- The local shell did not define `JAVA_HOME` during read-only class inspection. The installed JDK 17 executable was resolved directly; `javap` confirmed both providers' camera/logo/theme signatures and Coil's software-bitmap APIs. No JDK setting was changed.
- Marker images are requested with hardware bitmaps disabled because marker artwork is composed through a software Canvas. This avoids a software-canvas/hardware-bitmap mismatch; actual rendering remains part of emulator validation.

## September 21 camera and motion verification

- Rechecked the official GoogleMap gesture, idle, padding and camera contracts above. The native regression drags the SDK map while an image is delayed, changes metadata and measured bottom padding, then releases the image and checks native pixels/clicks. Metadata and image completion must retain target and zoom. Bottom padding must retain horizontal framing, zoom, bearing and tilt; the test does not assume an undocumented exact vertical translation.
- [Android ValueAnimator](https://developer.android.com/reference/android/animation/ValueAnimator#areAnimatorsEnabled()) exposes the system animation setting from API 26. The app's existing selection and route-preview camera updates now choose an immediate move when animations are disabled. Normal animations remain unchanged; discovery already uses immediate camera updates and the app shell has no destination transitions.
- Google documents `moveCamera` as instantaneous and notes both `moveCamera` and `animateCamera` leave SDK follow mode. The helper replaces only the app-owned selection/preview updates; it does not add discovery work to native navigation or alter Navigator's existing guidance lifecycle.
- The final source audit found that the discovery adapter applied native map appearance, but selection, preview and road navigation did not. Rechecked [navigation UI controls](https://developers.google.com/maps/documentation/navigation/android-sdk/controls), [lighting modes](https://developers.google.com/maps/documentation/navigation/android-sdk/lighting-modes) and [NavigationView](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/libraries/navigation/NavigationView): navigation does not directly follow system dark mode, and `setForceNightMode` is global. Both existing map wrappers now update browsing theme on their current live map; only the navigation-enabled Google wrapper updates forced day/night. Appearance changes do not recreate the view or touch destinations/camera.
- An initial native test waited for night-mode events without creating a Navigator and timed out. Official `setNavigationUiEnabled` documentation explicitly says the requested UI is only enabled after a Navigator exists. A view-only fixture therefore cannot prove active navigation night mode. The local test now explicitly covers browsing color-scheme changes and immediate reduced-motion camera behavior; forced navigation night-mode observation remains with the signed candidate's Navigator readiness checks. It does not create a route or accept new terms to bypass that prerequisite.
- Rechecked [CameraUpdateFactory](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/CameraUpdateFactory) and [LatLngBounds.Builder](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/model/LatLngBounds.Builder) before the final native FitAll regression: the padded bounds overload needs a laid-out map, and bounds construction selects the minimum east/west extension across the date line. The synthetic test first frames the date-line subset, then all members including a distant outlier using measured asymmetric padding; it checks membership, projection, unchanged Double bits and the outlier's native pixels/click.
- Before the remaining cluster/minimum-pan regressions, rechecked [OnMarkerClickListener](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/GoogleMap.OnMarkerClickListener) and [GoogleMap](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/GoogleMap). Consuming a marker click suppresses automatic recenter/info-window behavior; the native maximum zoom depends on camera position/map type. Tests therefore use real native touches, query the actual maximum, and measure visible/covered anchors against the current padded content rather than assuming a universal zoom or screen offset.

## Marker text scaling follow-up

The final requirement review found that bitmap labels/counts used fixed density-only text sizes. Compose page font tests do not establish bitmap font scaling. The follow-up uses the actual Compose sp conversion and measured bitmap geometry, retaining source coordinates and bitmap geographic anchors while updating collision bounds and appearance invalidation. The current official [FontScaling contract](https://developer.android.com/reference/kotlin/androidx/compose/ui/unit/FontScaling) was checked: the supplied Density conversion preserves Android's nonlinear font scaling instead of manually multiplying density and fontScale. Minimum bitmap dimensions alone do not prove native hit behavior.

Before extending native touch/anchor regression, the current [Marker](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/model/Marker) and [MarkerOptions](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/model/MarkerOptions) references were checked: the normalized bitmap anchor identifies the point placed at the geographic position, and native marker operations belong on the UI thread. No undocumented transparent-pixel hit tolerance is assumed. Both APIs passed the updated Google fixture: actual off-dot label touches, the enlarged border's native pixels, a doubled-font transition and retained View/anchor/camera/image-request assertions. The repaired signed candidate also passed that presentation fixture on API 37 ARM AMap; API 26 native-AMap coverage remains open. Exact hashes, the initial AMap tap timeout and separate workload results are in the acceptance log.

## AMap readiness and camera completion

The first usable signed ARM run rendered AMap tiles but timed out before publishing the focused member. Before repairing this path, the current official [GoogleMap camera contract](https://developers.google.com/maps/documentation/navigation/android-sdk/reference/com/google/android/gms/maps/GoogleMap), [AMap initialization/projection contract](https://a.amap.com/lbs/static/unzip/Android_Map_Doc/3D/com/amap/api/maps/AMap.html), [AMap camera-finish listener](https://a.amap.com/lbs/static/unzip/Android_Map_Doc/3D/com/amap/api/maps/AMap.OnCameraChangeListener.html) and [Android native-library lookup](https://developer.android.com/reference/dalvik/system/BaseDexClassLoader#findLibrary(java.lang.String)) were checked.

Google's synchronous move behavior is retained. AMap now waits for a map-loaded event registered before attachment, then a valid projection and an attached/resumed, non-retired lease. An AMap focus waits for a matching center completion before computing its padding pan, then waits for the final camera state before acknowledging it. Focus, locate, cluster zoom and single-point fit share that sequence. New requests, gestures, disposal and pending geometry changes invalidate stale work; settled views are not recentered merely for ordinary panel changes. Source coordinates and the map rotation pivot are unchanged.

The pinned AMap map library contains only ARM/ARM64 binaries. A privacy-ordered public classloader lookup rejects unsupported installation ABIs before SDK View construction and reports normal map unavailability, without changing consent or removing other APK architectures. A genuine ARM SDK execution is still required for AMap projection acceptance; an unsupported-ABI fallback test is not a substitute. Scalar-only native timeout diagnostics expose counts/readiness/containment booleans, never coordinates, credentials or provider response bodies.

At repaired source `cb89265`, signed run `35557984317` produced independently verified artifacts. API 37 ARM passed the three AMap projection/presentation, marker-metadata and provider-lifecycle cases; API 26 x86_64 passed the one unsupported-ABI fallback case. The first ARM suite had an isolated initial-tap callback timeout after its projection/centering/pixel checks passed; unchanged artifacts subsequently passed the individual case, full suite and visual capture. No specific cause or further code correction is claimed. The original readiness timeouts did not recur in these repaired runs. API 37 Google native/performance and Navigator-ready theme checks also passed; full artifact provenance and evidence limits remain in the acceptance matrix.
